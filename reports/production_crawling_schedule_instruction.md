# 운영용 크롤링 스케줄 및 수집 정책 지시서

작성일: 2026-07-05

## 1. 목적

이 문서는 법원 회생/파산 공고 수집을 실제 운영에 맞게 정기화하기 위한 지시서다.

현재 프로젝트는 개발 중 수동 실행 중심으로 크롤링을 해왔지만, 운영 단계에서는 다음이 필요하다.

- 언제 크롤링할지
- 얼마나 자주 크롤링할지
- 실패하면 어떻게 재시도할지
- 중복 수집을 어떻게 막을지
- 분석 job과 어떻게 연결할지
- 관리자 화면에서 수집 상태를 어떻게 볼지

## 2. 업무 특성 정리

회생/파산 공고는 실시간 경쟁성이 높은 데이터가 아니다.

현재 운영 가정:

```text
등록량:
  하루 약 10~20건

등록 시간:
  주로 평일 낮 시간대

긴급성:
  즉시 봐야 하는 정보는 아님

운영 전략:
  사용량이 적은 새벽 시간대에 정기 수집해도 충분함
```

따라서 너무 자주 크롤링할 필요가 없다. 서버와 대상 사이트에 부담을 줄이고, 운영 안정성을 우선한다.

## 3. 권장 크롤링 정책

### 3.1 1차 운영 정책

처음 운영은 새벽 시간대 1시간 간격 수집을 권장한다.

권장 시간:

```text
01:00
02:00
03:00
04:00
05:00
06:00
```

이유:

- 사용자 접속이 적다.
- 법원 공고 등록이 몰리는 평일 낮 시간과 분리된다.
- 수집 실패 시 같은 새벽 시간대에 재시도 기회가 있다.
- 분석 job이 새벽에 쌓이고, 오전에 결과를 볼 수 있다.

### 3.2 대체 정책

운영 안정화 후에는 다음 중 하나로 조정할 수 있다.

```text
보수적 운영:
  02:00, 04:00, 06:00

기본 운영:
  01:00~06:00 사이 1시간 간격

확장 운영:
  01:00~06:00 1시간 간격
  12:30 1회
  18:30 1회
```

현재는 기본 운영을 권장한다.

## 4. 평일/주말 정책

평일:

```text
새벽 01:00~06:00 사이 1시간 간격 수집
```

주말/공휴일:

```text
02:00 1회만 수집
```

이유:

- 주말에는 신규 등록이 적거나 없을 가능성이 높다.
- 완전히 끄면 금요일 늦은 등록이나 예외 데이터를 놓칠 수 있다.
- 1회 수집으로 최소 확인만 한다.

공휴일 판단이 복잡하면 1차에서는 요일 기준만 적용한다.

## 5. 수집 범위

### 5.1 기본 범위

매 수집마다 너무 넓은 기간을 다시 긁지 않는다.

권장:

```text
최근 14일
또는 마지막 성공 수집 시각 이후
```

1차 구현:

```text
최근 14일 기준 + file_hash/case_number 중복 방지
```

2차 구현:

```text
last_successful_crawl_at 이후 기준
```

### 5.2 2026-06-15 이후 재수집

현재 프로젝트에는 2026-06-15 이후 확장 수집 요구가 있다.

운영 스케줄과 별도로 “보정 수집”으로 분리한다.

```text
정기 수집:
  최근 데이터 유지

보정 수집:
  2026-06-15 이후 누락 데이터 보완
```

보정 수집은 새벽 정기 수집과 동시에 돌리지 않는다.

권장:

```text
일요일 새벽 03:00
또는 수동 실행
```

## 6. 중복 방지 정책

수집은 여러 번 실행되어도 DB가 오염되지 않아야 한다.

중복 판단 기준:

```text
1순위: raw_documents.file_hash
2순위: asset_events.case_number
3순위: source_url + attachment_name
```

동작:

```text
이미 같은 file_hash가 있으면 raw_documents 추가 안 함
이미 같은 case_number가 있으면 asset_events 추가 안 함
기존 데이터의 메타데이터가 부족하면 보강만 수행
```

## 7. 분석 job 연결 정책

크롤링이 끝났다고 바로 사용자 요청 안에서 분석하지 않는다.

권장 흐름:

```text
크롤링 완료
-> 신규 문서 저장
-> 텍스트 추출
-> 기본 분석 또는 분석 대기 표시
-> 상세 분석 job 생성 여부 판단
-> 로컬 분석 워커가 켜져 있으면 처리
-> 워커가 꺼져 있으면 PENDING 유지
```

분석 job 자동 생성 정책은 운영 부담에 따라 선택한다.

1차 권장:

```text
신규 수집 문서는 기본 분석까지만 수행
상세 분석은 관리자 또는 사용자 요청 시 job 생성
```

2차 권장:

```text
분석 가치가 있어 보이는 문서만 자동 상세 분석 job 생성
```

자동 상세 분석 조건 예시:

```text
텍스트 추출 성공
중복 문서 아님
마감일이 남아 있음
최저가 추출 가능
기본 리스크가 너무 높지 않음
```

## 8. 스케줄 실행 방식

### 8.1 1차: Windows 작업 스케줄러

로컬 운영 기준에서는 Windows 작업 스케줄러가 가장 단순하다.

실행 대상:

```powershell
cd C:\Users\xogns\Documents\testAuction\court_auction_platform
.\run_pipeline.ps1
```

또는 수집 전용:

```powershell
cd C:\Users\xogns\Documents\testAuction\court_auction_platform
.\collect_since_2026_06_15.ps1 -Limit 50 -MaxPages 15
```

정기 운영용 스크립트는 별도로 만드는 것을 권장한다.

권장 파일:

```text
run_scheduled_crawl.ps1
```

역할:

```text
1. 이미 실행 중인 수집이 있는지 확인
2. 수집 시작 로그 저장
3. 최근 범위 수집 실행
4. 결과 요약 저장
5. 실패 시 오류 저장
6. 종료
```

### 8.2 2차: 앱 내부 스케줄러

운영이 안정되면 FastAPI 앱 또는 별도 scheduler 프로세스에서 스케줄을 관리할 수 있다.

단, 1차에서는 앱 내부 스케줄러보다 Windows 작업 스케줄러를 권장한다.

이유:

- 웹앱이 꺼져도 스케줄 관리가 독립적이다.
- 로컬 운영에서 설정이 단순하다.
- 문제 발생 시 수동으로 확인하기 쉽다.

## 9. 수집 상태 저장

정기 크롤링을 운영하려면 실행 이력을 DB에 남겨야 한다.

권장 테이블:

```text
crawl_runs
  id
  run_type
  status
  started_at
  finished_at
  target_start_date
  target_end_date
  pages_scanned
  documents_found
  documents_downloaded
  documents_inserted
  duplicates_skipped
  failed_downloads
  error_message
  log_path
```

`run_type`:

```text
scheduled
manual
backfill
retry_failed
```

`status`:

```text
RUNNING
SUCCEEDED
FAILED
PARTIAL
```

## 10. 관리자 화면 반영

관리자 메뉴 중 `수집 관리`에 아래 정보를 표시한다.

```text
마지막 수집 시간
마지막 수집 상태
다음 예정 수집 시간
오늘 수집 문서 수
중복 제외 수
다운로드 실패 수
UNKNOWN 날짜 수
LOCAL_INGESTED 수
OCR 필요 수
최근 수집 로그
```

대시보드 첫 화면에는 요약만 표시한다.

```text
마지막 수집 성공: 2026-07-05 03:00
신규 문서: 12건
실패 다운로드: 1건
UNKNOWN 날짜: 3건
```

상세 목록은 `/admin/collection`에서 본다.

## 11. 실패 재시도 정책

수집 실패는 전체 실패와 부분 실패를 구분한다.

전체 실패:

```text
목록 페이지 접근 실패
사이트 접속 실패
파서 전체 오류
```

처리:

```text
FAILED 기록
다음 스케줄에서 재시도
관리자 화면에 표시
```

부분 실패:

```text
일부 PDF/HWP 다운로드 실패
일부 상세 페이지 파싱 실패
일부 날짜 추출 실패
```

처리:

```text
PARTIAL 기록
성공 데이터는 저장
실패 항목만 retry_failed 대상으로 저장
```

## 12. 부하 조절

크롤링은 대상 사이트와 로컬 서버에 부담을 주지 않아야 한다.

권장:

```text
요청 사이 1~3초 대기
한 번에 너무 많은 페이지 조회 금지
새벽 시간대 중심 운영
중복 파일은 다운로드 후 즉시 skip
실패 시 짧은 무한 재시도 금지
```

1차 제한:

```text
MaxPages: 15
Limit: 50
```

운영 데이터가 쌓이면 실제 등록량에 맞춰 더 낮출 수 있다.

## 13. 개발 순서

### Loop 1. 정기 수집 스크립트 추가

- `run_scheduled_crawl.ps1` 추가
- 실행 중복 방지
- 로그 파일 저장
- 최근 14일 수집 기본값
- 실패 시 로그 남김

완료 기준:

- 수동으로 실행 가능
- 중복 실행을 막음
- 성공/실패 로그가 남음

### Loop 2. crawl_runs 테이블 추가

- `CrawlRun` 모델 추가
- 수집 시작/성공/실패 기록
- 수집 요약 저장

완료 기준:

- 수집 실행 이력이 DB에 남음

### Loop 3. 관리자 수집 관리 화면

- `/admin/collection` 추가
- 최근 수집 이력 표시
- 실패 다운로드/UNKNOWN/LOCAL_INGESTED 요약 표시

완료 기준:

- 운영자가 수집 상태를 웹에서 확인 가능

### Loop 4. 스케줄러 설정 문서화

- Windows 작업 스케줄러 등록 방법 문서 작성
- 권장 실행 시간 정리
- 수동 실행/중지/재시도 방법 정리

완료 기준:

- 사용자가 새벽 정기 수집을 직접 등록할 수 있음

### Loop 5. 실패 재시도와 보정 수집

- 실패 다운로드만 재시도
- UNKNOWN 날짜 보정 대상 분리
- 2026-06-15 이후 보정 수집을 정기 수집과 분리

완료 기준:

- 정기 수집과 보정 수집이 서로 섞이지 않음

## 14. 권장 운영안

초기 운영:

```text
평일:
  01:00, 02:00, 03:00, 04:00, 05:00, 06:00

주말:
  02:00

보정 수집:
  일요일 03:00 또는 수동 실행
```

운영 안정 후:

```text
신규 등록량이 적으면 02:00, 04:00, 06:00으로 축소
낮 시간 확인이 필요하면 12:30 또는 18:30 1회 추가
```

## 15. 중요한 결정

회생/파산 공고는 실시간 대응보다 안정적인 누적 수집이 중요하다.

따라서 운영 기준은 다음으로 잡는다.

```text
빠른 수집보다 중복 없는 수집
많은 재시도보다 실패 항목 기록
실시간 분석보다 비동기 분석
한 화면 노출보다 관리자 수집 이력 관리
```
